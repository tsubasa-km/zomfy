# Worktree skills and worktree storage: Orca and Zomfy

Research note, 2026-11-25. Orca facts come from `stablyai/orca` at `main` (read through `gh api`) and
its docs sources under `docs/site/content/docs/`; Zomfy facts from this repository and the person's
machine. It answers two asks: (1) turn the worktree skill (and skills like it) on from Zomfy, and
(2) stop worktrees from eating the disk, after 28 worktrees of this repo (about 1–6 GB each:
`node_modules` per worktree, Rust `target/`, Expo `node_modules` past 260-character paths) had to be
cleaned up by hand.

## 1. Orca's skills

### 1.1 What ships

Three layers:

| Layer | Path | Role |
| --- | --- | --- |
| Stub sources | `skill-stubs/*.md`, `skill-stubs/_shared/cli-resolution.md` | Templates with shared blocks |
| Published stubs | `skills/<name>/SKILL.md` | Thin discovery stubs, generated by `config/scripts/skills/bundle-generation/skill-stub-composition.mjs` |
| Guides | `skill-guides/<name>.md`, `skill-guides/<name>/references/*.md` | The real instructions, embedded in the CLI binary and printed by `orca skills get <name>` |

`resources/skills/current-manifest.json` holds each stub's sha256, `released-digests.json` every
digest Orca ever shipped.

Skills: `orca-cli`, `orchestration`, `orca-computer-use`, `orca-linear`, `orca-jira`,
`linear-tickets`, `jira-tickets`, `orca-emulator`, `orca-emulator-android`,
`orca-per-workspace-env`, `orca-plugin-authoring`, and `orca-chat-visuals` (under
`resources/native-chat-visuals/`).

Every stub does the same three things: pick the executable (`ORCA_CLI_COMMAND`, `orca-dev` in a dev
checkout, `orca-ide` on Linux because bare `orca` is the GNOME screen reader, else `orca`); load the
version-matched guide with `orca skills get <name>` before running anything; and handle
`runtime_unavailable` / `runtime_access_denied`. Keeping the instructions in the binary means a stub
never drifts from the CLI that runs its commands, and stubs rarely need updating.

### 1.2 The worktree skill (`orca-cli`) and `orchestration`

- **`orca-cli`** triggers on "Orca worktree", "child worktree", "spawn codex/claude in a worktree",
  "handoff", and says *prefer it over raw git worktree*. Its guide defines a handoff as done once the
  worktree id and agent handle are reported, without waiting. Commands: `orca worktree create --name
  <task> --no-parent --agent codex --prompt "…" --json` (`--parent-worktree active`, `--pr 123`,
  `--model`, `--effort`), `orca agent launch --worktree <selector>`, `worktree
  list/ps/current/show/set`, `worktree rm --worktree <selector> --force` (refuses `current`).
- **`orchestration`** covers supervised parallel work: `orca orchestration worker-start --spec
  "<task>" --worktree current --agent <agent>`, about four workers at once, end the turn and be woken;
  workers use `ask` and `worker_done`; references on teardown, recovery (`worker-release`, a
  three-strike circuit breaker, `orchestration reset`) and parallel start are read on demand.

Zomfy's equivalents are harness MCP tools, not a CLI: `create_workspace` / `create_session` (a
handoff), `split_work` (supervised parallel parts, merged back by Zomfy), `finish_worktree`,
`claim_worktree`, `send_prompt`, `wait_for_session`.

### 1.3 How Orca installs, enables and updates them

- **Where.** `src/shared/skills/installation/skill-install-providers.ts` and
  `src/main/skills/providers/skill-provider-destinations.ts`. The canonical copy is always
  `<scope>/.agents/skills/<name>`, which Codex and several others read directly; agents with their own
  folder (Claude Code `~/.claude/skills` or `$CLAUDE_CONFIG_DIR/skills`, Cursor, Droid, Kiro,
  Antigravity, …) get a link to it.
- **Scope.** `global` (the home) or `workspace` (a project). A project install links only into agent
  folders that project already has (`bundled-skill-targets.ts`).
- **Link, else copy.** `src/main/skills/filesystem/skill-native-alias.ts`: a junction on Windows (no
  admin rights needed), a relative symlink elsewhere; a host that cannot link gets copies
  (`bundled-skill-plan.ts`).
- **Updates without a version file.** Each installed `SKILL.md` is hashed (LF-normalised sha256) and
  classed as `current`, `released` (an older Orca's), `edited`, `other-build` or `other`
  (`bundled-skill-classification.ts`). Only a folder that holds nothing but an unedited released stub is
  overwritten in place; an edited or foreign one is left alone unless the person picks **Replace** (or
  `--force`), which first backs it up to `~/.agents/.orca-skill-backups/`. A plan is pinned to the
  digests it was previewed with ("Changed since you reviewed it").
  `autoUpdateInstalledBundledSkills` runs from the renderer
  (`skills/freshness/skill-freshness-auto-update.ts`), with `SkillFreshnessNudge` and an "Update
  skills" dialog.
- **UI.** Settings → General → Command line (`settings/cli/install/CliSection.tsx`): a PATH switch
  and `AgentSkillSetupPanel` (install state of `orca-cli`); `OrchestrationSkillPromptDialog`;
  `SkillInstallDialog` (agents, machine, workspace); the Skills page (Delete, Manage installs, Share).
- **CLI.** `orca skills install --skill orca-cli --agent claude,codex [--local]`, `orca skills update
  --all [--dry-run|--force]`; also `npx skills add https://github.com/stablyai/orca --skill orca-cli
  --global`.
- **No install at all** for Orca's own ACP chats: `src/main/acp/launch/acp-skill-roots.ts` hands the
  skill roots to the agent's launch (plugin dir and the like).
- **The CLI** comes with the desktop app and is put on PATH from that switch (`src/main/cli/*`; a
  symlink on macOS, `~/.local/bin/orca-ide` on Linux, the user PATH in the registry on Windows; WSL
  has its own installer). Orca's terminals have it already.

## 2. How Orca keeps worktrees off the disk

What exists:

- **Automatic cleanup, off until turned on** (`src/shared/workspace-cleanup/workspace-cleanup-policy.ts`,
  runner `src/main/workspaces/cleanup/workspace-cleanup-runner.ts`: first run 2 minutes after start,
  then hourly). Rules: `merged`, `unchanged` for N days, `inactive` for N days (delete or archive),
  automation runs, orchestration workers; `keepWhen` `uncommitted` or `any-local-files`; per-project
  off or custom. Always kept: pinned, running agents or terminals, unsaved editors, uncommitted or
  unpushed work. Merged branches are deleted, unmerged ones kept. UI
  `settings/workspace-cleanup/WorkspaceCleanupSettingsPane.tsx` ("Automatic cleanup", "Run rules
  now", "Last run … freed {size}"); CLI `orca workspace cleanup preview|run|report`.
- **Manual cleanup**: Resource Manager → **Clean up workspaces**
  (`workspace-cleanup/WorkspaceCleanupDialog.tsx`), sortable and filterable by state, activity, **size**
  and git state; branches it kept are offered later from a "Review N Branches" toast.
- **Size per worktree**: the status bar's workspace storage view (treemap and table,
  `status-bar/workspace-storage/`), scanned in a worker (`src/main/workspaces/space-analysis/`) within a
  budget of 100k entries per directory and 64 MiB of scan state.
- **Hooks**: `orca.yaml` `scripts.setup` / `scripts.archive`; archive runs before a removal and a
  failure stops it. Settings → Repository picks run / ask / skip for setup.
- **Shared dependencies**: Worktree Shared Paths in Settings → Repository and `orca.yaml`
  `worktree.sharedDirectories` link directories such as `node_modules` from the main checkout (APFS
  clone or symlink; a junction first on Windows).
- **`.worktreeinclude`**: copies gitignored files, literal paths, within 2 GiB / 50,000 entries per
  worktree (`worktree-include-copy-budget.ts`).
- **Windows deletion**: `src/main/filesystem/host-tree-removal.ts` deletes through `\\?\` paths
  (`win32.toNamespacedPath`), retries the whole removal on EBUSY / EPERM / ENOTEMPTY, deletes `.git`
  last, and names the file another program holds open. Also: two removals at a time
  (`worktree-delete-limit.ts`), background removal that survives a quit
  (`worktree-background-removal.ts`), orphaned-worktree cleanup (`local-orphaned-worktree-cleanup.ts`).

What does not: archiving (`WORKSPACE_ARCHIVE_SUPPORTED = false`, the archive action is skipped), a
free-space warning or check before creating a worktree, any quota, and a shared dependency store of
Orca's own (pnpm's store is left to the project).

## 3. What Zomfy has today

### 3.1 Skills

- **The "worktree skill" on this machine is Orca's.** `~/.agents/skills/` holds `orca-cli`,
  `orchestration` and `computer-use`, installed on 2026-10-19 by `npx skills add` from `stablyai/orca`
  (`~/.agents/.skill-lock.json` records the source, ref and folder hash). They are stubs that run the
  `orca` executable, which is not on PATH here (Orca is installed under `%LOCALAPPDATA%\Programs\orca`
  but its CLI switch is off). Codex and other `.agents` readers see them; Claude Code reads
  `~/.claude/skills` and does not. In a Zomfy chat they point an agent at the wrong tool: they say
  to prefer `orca worktree` over everything else, and Zomfy's worktrees are not Orca's.
- **Zomfy ships no skill of its own.** The repo's only skills are `.claude/skills/okf-*` for this
  project's docs. What tells an agent about worktrees is text the daemon adds to each chat's
  instructions (`worktree-claims.ts` "this project has other worktrees…", `split-work.ts` "you can run
  parts of a large task…", `project-agent-tools.ts` for tools a project turns off) plus the harness
  MCP tools themselves.
- **The Skills page** (`apps/desktop/src/components/skills/`, `settings/SkillsPane.tsx`) is Orca's
  discovery ported: `packages/daemon/src/skill-discovery.ts` scans home and project skill folders for
  Codex, Claude Code (and its enabled plugins) and the Orca provider list;
  `handlers/skill-handlers.ts` offers `skills/discover`, `read`, `trash` and `copy` (copy a found skill
  into other agents' folders, never over one there; `apps/desktop/tests/skill-copy-targets.test.ts`).
  There is no bundled skill, no install-by-name, no link, no update, no enable or disable.

### 3.2 Worktrees and the disk

- **Where**: `~/zomfy/workspaces/<project>/<name>` (or the project's `worktreeRoot`), made by
  `git -c core.longpaths=true worktree add` in `workspace-manager.ts` `createWorkspace`.
- **Setup**: `zomfy.yaml` / `orca.yaml` `scripts.setup` runs in a terminal of the new worktree
  (`project-hooks.ts`); this repo has none, so each chat runs `bun install` itself, and a full
  `node_modules` (plus `apps/mobile`'s Expo tree and, after a desktop build, a Rust `target/` of
  several GB) lands in every worktree. Nothing is shared or linked.
- **`.worktreeinclude`** (`worktree-include.ts`) copies gitignored files the patterns match, with no
  size budget; this repo has no such file.
- **Removal**: `finish_worktree` in merge mode, and `split_work` after it merges a part, remove the
  worktree and branch (`harness-agent.ts`, `split-coordinator.ts`), running the archive hook first.
  In pull-request mode, a worktree made with `create_workspace` or by the person, or work merged by
  hand, the worktree stays until the person deletes it.
- **Clean Up Merged Workspaces** (`sidebar/CleanupMergedDialog.tsx`) offers worktrees whose summary
  says `merged` (no changes, nothing ahead of the base, `workspace-git-summary.ts`). The base is the
  project's `defaultBaseRef`, else `origin/HEAD`, else `origin/main` … `main`
  (`workspace-manager.ts` `defaultBaseRef`). This repo's remote is `github`, not `origin`, so the base
  falls to local `main` — the *released* branch — while topic branches merge into `development`.
  **A branch merged into `development` does not count as merged until the next release**, which is
  why the dialog found little to clean and 28 worktrees piled up.
- **Long paths**: commit `de87c41` (2026-11-25) runs `git worktree remove` with `core.longpaths` and
  deletes a folder git no longer knows with `rm -r`. Leftovers remain: six folders under
  `~/zomfy/workspaces/acp-harness/` (`bots-b0`, `bots-b1-daemon`, `bots-b1-discord`, `pane-sidebars`,
  `retire-old-home`, `usage-and-mcp-icons`) are no longer worktrees and hold no files, only about 300
  empty nested `node_modules` folders each — the remains of an earlier delete that gave up.
- **None of**: size per worktree, a free-space warning, an idle policy, removing `node_modules` /
  `target/` from an idle worktree, shared dependencies.

## 4. What this suggests

1. A **Zomfy skill** should describe the harness MCP tools, not a CLI, so it needs no PATH and no
   version-matched guide; the chat instructions already carry most of it, and the skill earns its
   place for agents that do not get those instructions (a terminal agent in a worktree, Codex, a chat
   opened outside Zomfy) and to warn off Orca's `orca-cli` stub where `orca` is absent.
2. Orca's install model (canonical `.agents/skills` + junction/symlink per agent, digest-classified
   updates, never overwriting an edit, backups) is worth copying whole; Zomfy's `skills/copy` is the
   start of it.
3. The biggest disk win is cheap: **compute "merged" against the branch work is finished into**
   (`development` here), then offer — or by policy perform — the cleanup. Next: show sizes, strip
   `node_modules` and `target/` from idle worktrees, and share dependencies (bun's global cache with
   hardlinks; a shared Cargo `target/`), with a free-space warning before a new worktree.
